# Agent Note: Desktop automatic updates from GitHub Releases

Status: implemented

English | [中文](2026-08-14-desktop-automatic-updates.zh.md)

## Problem

The packaged desktop application gave users no controlled path from an installed version to a later release. Finding a release, selecting the correct architecture, replacing a running application, and preserving Host work were all left to the user. Adding a network check alone would not solve the lifecycle problem: update feed identity, download consent, platform artifact identity, shutdown ordering, and publication completeness must agree or the application can offer an incomplete or misdirected upgrade.

## Decision

The Electron main process owns one `electron-updater` controller backed by GitHub Releases. Build-time resources pin the repository and channel, enable updates only for official release packages, and carry bounded scheduling values. Runtime parsing rejects malformed repository segments, channel names, delays, and release URLs. The feed does not use a GitHub token at runtime, and the controller rejects prereleases and downgrades.

`@deepseek-ai/dsh-client-connection` owns the shared `DesktopUpdatePolicy`, action, state, and preload-bridge protocol plus its IPC parsers, so the Electron main process, preload, and renderer use one process-neutral definition without importing a UI aggregate. `@deepseek-ai/dsh-client-ui-desktop-update` registers the `desktop-update` namespace with its durable `policy` field and the Desktop-only renderer surfaces, but no Cordis Context service. The Electron main process reads the resolved policy through the generic settings service and adapts `settings/updated` events to the local updater controller. The policy is one of `background`, `startup`, `manual`, or `disabled`; `background` is the default. It checks after a 30-second startup delay and then every four hours, `startup` checks once after the delay, `manual` checks only after a user action, and `disabled` stops future checks. The main process publishes a revisioned closed state machine: `disabled`, `idle`, `checking`, `available`, `downloading`, `ready`, and `error`. Background up-to-date and error results stay silent; manual results and actionable versions appear in a non-modal `shell.overlay` notice and the General Settings row.

`autoDownload` and `autoInstallOnAppQuit` are disabled. Finding a release exposes a download action; reaching `ready` exposes a separate restart-and-install action. Disabling future checks does not revoke an update that is already available or downloaded. An ordinary app quit never installs an update by accident.

## Lifecycle and platform support

The application takes a single-instance lock before booting the Host so only one process owns updater state and its cache. Signals, window quit, startup failure, in-profile `appExit`, and requested installation converge on one shutdown coordinator. Desktop selects the `{ kind: 'caller' }` profile lifecycle: `attach` supplies the bounded shutdown before profile boot can yield, and `requestExit` routes `appExit` to Electron. A shutdown requested during startup waits for the profile Context to be published before disposing it, then blocks the remaining updater, IPC, and window bootstrap; the controller never changes process exit state. Installation stops updater scheduling and aborts active application work; local cleanup failures are reported while later cleanup and Host quiescence still proceed. Error reporting is best-effort and cannot interrupt that sequence. Only successful cleanup and Host quiescence allow `quitAndInstall(false, true)` to run. Desktop then waits up to the build-pinned two-minute limit for the native `before-quit-for-update` acknowledgement. Cleanup failure, disposal failure, or quiescence timeout prevents installer invocation; a handoff error or acknowledgement timeout makes Electron exit nonzero. A second quit request joins the same promise instead of starting parallel teardown.

Official macOS and Windows packages support in-place updates. A Mac package runs its updater only from `/Applications` or the current user's `Applications` directory. Arm64 uses channel `latest-arm64` and document `latest-arm64-mac.yml`; x64 uses `latest-x64` and `latest-x64-mac.yml`, so concurrent release jobs cannot overwrite one architecture's channel document with the other. Windows x64 uses `latest.yml` plus the NSIS `.exe.blockmap`. The Linux `.tar.gz` has no channel document or safe replacement installer, so its state is `disabled` with reason `unsupported-platform` and its Settings action opens the pinned GitHub Releases page for manual installation.

The first update-enabled release is a seed version that users install manually; the next higher release is the first one able to prove the in-place path. Rollback is another higher patch release, never a downgrade. This keeps version ordering monotonic and avoids teaching the client to accept an older artifact after a compromised or defective release.

## Trust and publication

The context-isolated preload exposes only state retrieval, state observation, and the closed `check`, `download`, `install`, and `open-release` action set. Its CommonJS artifact bundles the process-neutral connection parser instead of requiring that package's ESM subpath at runtime. The main process validates the sender with the same owning-window, top-frame, and `dsh://app` checks as other privileged IPC. The renderer parses every structured-clone state before rendering it, rejects stale revisions, and accepts only the build-pinned HTTPS `github.com/<owner>/<repository>/releases` path. The main process alone opens that page in the operating-system browser and owns all updater network and installer calls.

Release packaging adds Electron Builder channel metadata and integrity hashes beside the distribution assets. The workflow classifies only a pushed tag as a release build and separately validates a source-controlled signing mode. The current [certificate-free release-mode decision](../process/2026-08-15-certificate-free-desktop-release-mode.md) selects certificate-free mode and separately limits publication to `dsh-v0.1.1`: Mac applications use one stable ad-hoc designated requirement without Developer ID authentication or notarization, while Windows applications and NSIS installers are unsigned and omit `publisherName`. Manual dispatches use the same certificate-free package verification but never publish. Explicit `signed` mode alone injects signing and notarization secrets, derives the Windows certificate's full X.509 Subject into `publisherName`, and fails when any required credential or publisher identity is missing; missing secrets never select certificate-free mode.

The final publisher binds to `desktop-release`; for certificate-free `0.1.1`, it references no signing secret and has no manual approval requirement. Certificate-free Mac and Windows package jobs, Linux package jobs, and manual jobs bind to the secret-free `desktop-package` Environment. Before selecting `signed`, maintainers configure `desktop-release` with required reviewers, no self-review or protection-rule bypass, a selected `dsh-v*` Tag deployment rule, and all Apple and Windows signing and notarization secrets, with no repository- or organization-level copies. The signed Mac and Windows package jobs then bind to that Environment, and a repository ruleset restricts `refs/tags/dsh-v*` creation while blocking updates and deletion.

A release tag is exactly `dsh-vX.Y.Z` and must equal a stable `X.Y.Z` desktop package version; prerelease versions are rejected before packaging. Each Mac or Windows package job parses the generated updater document and verifies its exact platform file set, primary path, sizes, and SHA-512 digests before artifact upload. All native build and packaged-smoke jobs finish before publication. The publisher validates one complete, non-duplicated cross-platform asset set, writes `SHA256SUMS`, creates a draft GitHub Release, uploads every installer, archive, update document, and blockmap, and converts the draft to a public release only after all uploads succeed. Once public, that tagged Release is immutable: a workflow rerun fails rather than accepting or replacing its assets. A failed validation or upload therefore cannot expose a public partial channel.

## Verification

Controller tests pin policy adoption, scheduling, state transitions, quiet background outcomes, explicit download, clean-shutdown delegation, duplicate backend-error suppression, and disposal. Caller-owned shutdown tests pin successful quiescence, disposal rejection, timeout rejection, synchronous re-entry coalescing, and the absence of process-exit effects. Connection protocol and UI client-controller tests pin IPC validation and stale-revision rejection; presentation and slot-composition tests pin the two visible surfaces. The packaged desktop smoke enters the real `dsh://app` composition, verifies that the updater bridge returns a valid state, and then evaluates `process.emit('SIGTERM')` through the loopback-only main-process inspector opened by `--inspect=0`. This directly exercises the registered signal shutdown path without entering Chromium's browser-close lifecycle. The child must emit `close` within five seconds with `exitCode === 0` and `signalCode === null` plus the main-process `dsh desktop: shutdown quiesced` marker emitted after cleanup and Host quiescence succeed; `SIGKILL` is failure cleanup only. The release workflow independently checks stable version/tag equality, native packaging, exact asset counts, feed path, size, and SHA-512 equality, checksums, and published-Release immutability before publication.

Installing and uninstalling every container format, a real two-version update through a public GitHub Release, operating-system trust prompts on a recipient machine, and recovery from interruption inside a platform installer remain coverage gaps. The seed release plus its next release are the production proof of the complete update path.

## Alternatives considered

**Use Electron's bare `autoUpdater` and maintain provider logic locally.** Electron's API does not provide one consistent GitHub metadata, download-progress, and packaging integration across the shipped DMG/ZIP and NSIS formats. `electron-updater` consumes the metadata already emitted by Electron Builder and removes provider and installer orchestration that the repository would otherwise own.

**Download every update in the background and install on quit.** This reduces clicks but spends bandwidth without consent and makes an ordinary quit capable of changing the installed application. Explicit download and install actions keep both effects visible and give the Host shutdown coordinator one intentional installation path.

**Check GitHub from the renderer or a shared Web plugin.** That would give untrusted client code feed selection or network authority and would add desktop release behavior to browser deployments. A Desktop-only presentation plugin over a main-process controller keeps platform authority out of the renderer while reusing the existing slot and Settings systems.

**Publish each platform asset as soon as its job completes.** Users and updater clients could observe a release with missing architectures, metadata, or blockmaps. A draft is the staging transaction; exact-set validation and one final publish action make completeness a release invariant.

**Enable Linux replacement from the `.tar.gz`.** The archive has no installation root, package-manager ownership, or atomic swap mechanism. Opening the published release page with its checksum for manual installation is honest about that limitation; in-place Linux updates require a future installer format with its own lifecycle decision.

**Allow downgrade for rollback.** It would make a known older build reachable, but it also weakens monotonic version selection and keeps old update metadata security-relevant. A higher patch release restores the desired code without changing the client trust rule.

## Consequences

Mac and Windows users get a durable update policy, quiet periodic checks, explicit download, and installation only after Host quiescence. The updater cannot silently redirect its feed from renderer input, the browser product gains no update behavior, and public GitHub Releases appear only with a complete asset set whose selected Mac and Windows signature state has been verified. The capability adds no model-visible prompt, message, tool, schema, or provider-request content.

The cost is architecture-specific Mac channels, a seed-release bootstrap, larger release asset sets, an additional long-lived main-process state machine, and operating-system trust warnings while certificate-free mode is selected. Linux users still install updates manually, ordinary local packages cannot exercise the enabled feed, and full confidence in platform replacement requires observing the seed-to-next-version release pair. Switching to signed releases additionally requires platform signing and notarization infrastructure.
